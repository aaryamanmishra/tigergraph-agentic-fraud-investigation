# Dataset Discovery & Exploratory Analysis
## TigerGraph × Hacker House Goa 2026 — HHGOA_IEEE Package

### 1. Dataset Overview & Inventory

The dataset represents six months of credit and debit card transactions from July 2, 2016 through December 31, 2016. Derived from the IEEE-CIS Fraud Detection dataset (Vesta Corporation), it preserves all original feature columns while integrating essential institutional fraud investigation context: synthetic customer mapping, real calendar timestamps, payment channels, model-generated risk scores, four months of historical closed cases, and a 20-case benchmark pack.

| File Name | File Size | Header Count | Row Count | Primary Key / Identifier | Description |
|---|---|---|---|---|---|
| `transactions.csv` | ~708 MB | 397 columns | 590,742 rows | `TransactionID` | Complete transaction stream across 6 months. Includes Vesta features + added fields. |
| `identity.csv` | ~26.7 MB | 41 columns | 144,432 rows | `TransactionID` | Identity, connection, and device attributes for online transactions (`ProductCD != 'W'`). |
| `closed_cases_history.csv` | ~2.7 MB | 15 columns | 5,565 rows | `case_id` | Historical investigations concluded July–October 2016 (4,665 confirmed fraud, 900 cleared). |
| `case_pack.csv` | ~3.5 KB | 8 columns | 20 rows | `case_id` | The official hackathon benchmark cases (HHG-001 through HHG-020) from November–December 2016. |

#### 2.1 Customer and Card Architecture
- **Customer ID (`customer_id`)**: Formatted as `Cxxxxx` (e.g. `C12382`, `C13487`). Exactly 13,553 unique customers exist across the 590,742 transactions.
- **Card Identifier (`card_id`)**: Formatted as `<customer_id>-K<index>` (e.g. `C12382-K1`, `C08623-K2`).
- **Card Relationship**:
  - `card1` represents the unique issuer bank card portfolio/bin hash. In this dataset, `card1` is 1-to-1 with `customer_id` (13,553 unique values).
  - Sub-cards (`-K1`, `-K2`) reflect secondary cards held by the customer, distinguished by sub-issuer attributes (`card2` through `card6`), or card reissues following compromise.
  - In `case_pack.csv` and `closed_cases_history.csv`, transactions are mapped to explicit `card_id` tags.

#### 2.2 Transaction Architecture
- **Time Range**: `2016-07-02 00:02:21` to `2016-12-31 23:58:54`.
- **Channels**:
  - `in_person`: Corresponds to `ProductCD = 'W'`. These transactions do not possess records in `identity.csv` and have no device footprints.
  - `online`: Corresponds to product codes `C`, `H`, `R`, `S`. These transactions link directly to `identity.csv` on `TransactionID`.
- **Risk Score (`risk_score`)**: A float in `[0.0, 1.0]` generated by the bank's real-time detection model.
  - **Critical Principle**: The README emphasizes that `risk_score` is an **imperfect trigger, not a verdict**. Above 0.70, many flagged alerts turn out to be legitimate (e.g. traveling customers or large routine purchases), whereas some confirmed fraud episodes have scores under 0.10. Never equate `risk_score > X` to fraud.

#### 2.3 Identity & Device Profile Architecture
- `identity.csv` contains 144,432 records.
- **Constructing the Canonical `DeviceProfile`**:
  Following the standard established in the hackathon README example (line 378), device identity is represented by the composite string:
  $$\text{DeviceProfile} = \text{DeviceInfo} \parallel \text{id\_30} \parallel \text{id\_31} \parallel \text{id\_33}$$
  *Example*: `SAMSUNG SM-G892A Build/NRD90M | Android 7.0 | samsung browser 6.2 | 2220x1080`
- **Key Identity Attributes**:
  - `id_15`: Device status relative to the account (`New` vs `Found`).
  - `id_23`: Proxy status (`IP_PROXY:ANONYMOUS`, `IP_PROXY:HIDDEN`, `IP_PROXY:TRANSPARENT`, or null).
  - `DeviceType`: `mobile` or `desktop`.
  - `id_34`: Match status (e.g. `match_status:2`).

### 3. Analysis of Historical Closed Cases (`closed_cases_history.csv`)

The closed cases dataset spans the first four months (July to October 2016) and contains 5,565 resolved investigations.

#### 3.1 Outcome and Pattern Breakdown

| Outcome | Pattern | Count | SAR Filed (`report_filed`) | Typical Analyst Finding |
|---|---|---|---|---|
| `confirmed_fraud` | `card_not_present_fraud` | 1,404 | 14 Yes / 1,390 No | Unrecognized online purchases inconsistent with cardholder baseline; 2–4 txn bursts. |
| `confirmed_fraud` | `account_takeover` | 1,205 | 187 Yes / 1,018 No | Mixed-channel activity; credential compromises; mismatched device and profile flags. |
| `confirmed_fraud` | `card_not_present_new_device` | 1,076 | 56 Yes / 1,020 No | Online charges originating from a device marked `New` or behind proxy. |
| `confirmed_fraud` | `out_of_region_use` | 955 | 124 Yes / 831 No | Card-present charges in distant billing regions while cardholder retained physical possession. |
| `confirmed_fraud` | `card_testing` | 16 | 7 Yes / 9 No | Rapid sequence of small authorizations (<$5) followed by large purchase attempt. |
| `confirmed_fraud` | `undocumented` | 9 | **9 Yes / 0 No** (100%) | Multi-card coordinated abuse (e.g. shared device/proxy across accounts) or structuring. |
| `cleared` | `none` | 900 | 0 Yes / 900 No | Legitimate false alarms: customer travel, new personal device confirmed, or routine spend. |
| **Total** | | **5,565** | **397 Yes / 5,168 No** | |

#### 3.2 Key Insights from Closed Cases
1. **SAR Filing Selectivity**: Only 397 of 5,565 cases (~7.1%) resulted in a regulatory report (`report_filed: Yes`). A SAR is filed only when exposure exceeds $\$1,000$, when shared infrastructure connects multiple victims, or when coordinated/undocumented abuse occurs.
2. **Undocumented Patterns Always Trigger SAR**: Every single historical `undocumented` case (9 out of 9) resulted in a filed report (`report_filed: Yes`) and involved coordinated abuse across multiple cardholders (e.g. Samsung SM-G935F behind anonymous proxy).
3. **Cleared False Alarms**: All 900 cleared cases had an exposure of $\$0.00$, actions `VERIFY_WITH_CUSTOMER|CLOSE_NO_FRAUD`, pattern `none`, and no SAR filed.

### 5. Semantic Interpretation of Feature Groups

| Column Group | Count | Interpretability | Role in Investigation Pipeline |
|---|---|---|---|
| `TransactionID`, `TransactionDT`, `TransactionAmt`, `ts` | 4 | **Full** | Foundational transaction identification, chronologically sequenced velocity analysis, and exposure calculation. |
| `ProductCD` | 1 | **Full** | Distinguishes channel: `W` is strictly in-person; `C`, `H`, `R`, `S` are online with identity tracking. |
| `card1` to `card6` | 6 | **High** | `card1` identifies customer issuer portfolio; `card4` is network (Visa, MC, Amex, Discover); `card6` is funding type (credit/debit). |
| `addr1`, `addr2` | 2 | **High** | `addr1` is regional billing code; `addr2` is country (87 is domestic home country). Key for out-of-region detection. |
| `dist1`, `dist2` | 2 | **Moderate** | Spatial distance indicators. High values signify physical geographic anomalies. |
| `P_emaildomain`, `R_emaildomain` | 2 | **High** | Email domains of purchaser and recipient. Essential for identifying shared fraud rings and throwaway domains. |
| `id_12` to `id_38`, `DeviceType`, `DeviceInfo` | 29 | **High** | Concrete device attributes: device model, browser version, OS, screen resolution, proxy flags, and `New` vs `Found` status. |
| `C1` to `C14` | 14 | **Signal Only** | Aggregated counts (phone/address associations). Interpreted strictly as numeric frequency signals. |
| `D1` to `D15` | 15 | **Signal Only** | Time deltas (days elapsed between transactions/events). Used for recency/dormancy analysis. |
| `M1` to `M9` | 9 | **Signal Only** | Binary match flags (e.g. name matching address). Discordance signals potential account compromise. |
| `V1` to `V339` | 339 | **Signal Only** | Engineered Vesta features. **Never assign speculative names or fabricated semantics to unnamed V-features**. Treat as mathematical risk signals. |
| `id_01` to `id_11` | 11 | **Signal Only** | Encoded ratings for device/IP/proxy. Negative or extreme scores indicate heightened anomaly. |

### 6. Data Integrity, Missing Values, and Quality Controls

1. **Identity Absence for In-Person Txns**: `ProductCD = 'W'` transactions (~74% of the dataset) inherently do not possess identity records in `identity.csv`. The pipeline must handle null device profiles gracefully without raising errors.
2. **Missing `addr1` in Online Txns**: Digital goods or cross-border purchases frequently lack billing region codes (`addr1 = null`). Out-of-region rules (R2, R3) must only fire when valid billing regions are present.
3. **Card Reissues & Sub-Cards**: Customers can possess multiple cards (`-K1`, `-K2`). Investigation of a single card must traverse to sibling cards owned by the same customer to verify compromise spread (Policy R10).
